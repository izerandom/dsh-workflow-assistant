01 / WHY

我们要解决的，不是“AI 不够聪明”

真正的风险来自目标漂移、范围膨胀、契约猜测和“测试通过就算完成”。工作流把这些风险前置、显式化。

没有流程

从一句话直接开工

需求没澄清，边界没写下，AI 只能猜。最后代码可能很多，但没人能说清“做完是什么样”。

有流程

从验收标准开始

先把可观察的结果写进工作单，再让接口、任务、测试和实现逐项对账。

协作收益

聊天不再是唯一记忆

每一轮 AI 只读工作单和相关代码。换人、换模型、隔天继续，都能从同一份事实出发。

治理收益

速度建立在可回退之上

发现设计错误时回退到接口设计；公共契约变更必须确认；高风险工作保留人工评审门。

02 / FLOW MAP

一条主线，两个闸门，一个循环

低复杂度走简化路径；中、高复杂度增加契约、人工评审和独立评审。质量底线不因“任务小”而消失。

03 / THE PLAYBOOK

七个环节，分别产出什么

每一步都有输入、动作和可交付产物。AI 可以推进动作，但不能替团队拍板未确认的决策。

01

需求对话：把“想要”变成“做完”

确认实现效果、范围边界、约束和可验证的验收标准。禁止“尽量”“基本可用”等模糊标准。

新需求开始前先只读检查工作区：若发现未提交改动，AI 会明确阻止开始并列出受影响文件；请先提交或 stash，完成后再重新开始。进行中的工作单回退或调整不受此门槛影响。

产物 → 工作单中的需求、AC1…ACn、明确不做的事
02

接口设计：先查已有契约，再决定新增

检查 OpenAPI、后端定义和团队约定。复用已有接口；确有新增时明确签名、字段、错误处理和兼容边界。

产物 → 可被逐条断言的接口 / 数据契约
03

任务拆分：按功能边界，不按文件切

将内聚需求拆成可独立实现、测试、验收的子任务，依赖清晰排序，一次只做一个切片。

产物 → 切片表 + 每个切片的正常、边界、错误用例
04

人工评审：中、高复杂度的实现闸门

工作单完整后交人评审。未通过就回退修改工作单，不进入实现。低复杂度只需一句话确认。

产物 → 明确的“通过 / 退回修改”决定
05

测试优先：先看到失败，再写最小实现

根据验收标准写测试，运行确认失败，再实现，最后运行确认通过。关注业务、边界、错误和契约，不追求虚假的覆盖率。

产物 → 可回归的测试 + 可复现的运行结果
06

独立评审：执行者和评审者不兼任

中、高复杂度由独立评审只读代码、契约和验收标准，不读实现者上下文。问题分为阻塞、建议、可选。

产物 → 具体到位置和契约条目的问题清单
07

最终验收：逐条对账，证据说话

逐项核对 AC，每条附测试输出、文件列表或手工验证记录。中、高复杂度还需要人最终确认。

产物 → 验收结果 + 遗留风险 + 交付信息

04 / HUMAN × AI

人机分工：AI 推进，人做决策

把人的时间放在不可委托的地方：目标、边界、契约和最终责任。

判据单点小改、无契约变化

如文案、单文件 bug、局部调整。

AI 负责需求确认 → 测试 → 实现 → 测试 → 验收

按简化路径执行，仍需可测标准和运行验证。

人负责一句话确认 + 最终使用反馈

不需要完整工作单评审和独立评审。

判据内聚功能、多文件或数据 / 接口变化

可以拆成多个有依赖的子任务。

AI 负责完整流水线 + 测试 + 独立评审准备

维护工作单，逐切片循环并提供证据。

人负责工作单评审 + 最终验收

在实现前和交付前各把一次关。

判据架构、公共契约、跨模块或多子系统

影响调用面、数据面或外部消费者。

AI 负责契约书面化 + 完整流水线 + 独立评审

不得猜字段，不得绕过验收门。

人负责设计决策、破坏性变更确认、最终签字

生产发布永远由人执行，Agent 没有生产钥匙。

05 / PROJECT KIT

把流程装进项目

工作流不是只靠 AI 对话推进，还需要项目里的几份配套文件共同提供上下文、格式和可视化入口。它们各司其职，不能互相替代。

项目规则 · 技术上下文

AGENTS.md

告诉 AI 这个项目“应该怎么写”：技术栈、目录结构、命名方式、类型约束、测试框架、构建命令和 Never 规则。它属于项目本身，优先级高于通用工作流。

视觉规则 · 设计令牌

DESIGN.md

告诉 AI 页面“应该长什么样”：颜色、字号、间距、圆角、阴影、字体和令牌消费方式。UI 实现前读取，避免每次临时发明视觉值。

协作格式 · 唯一工作单模板

worksheet-template.md

定义工作单的固定结构：进度、基本信息、需求、验收标准、边界、接口契约、任务切片、测试用例、最终验收和变更记录。每个新需求复制它，放进项目根目录 workorders/。

可视化入口 · 工作单助手插件

工作单助手（DeepSeek Harness 插件）

在 DeepSeek Harness 中加载的会话级插件：右下角悬浮胶囊实时显示待办数，点击展开面板——聚合「待评审 / 待验收」待办与全部工作单（状态按进度清单勾选数自动推断：未开始 / 确认中 / 实现中 / 待验收 / 验收中 / 已完成）。点开任意工作单即在浏览器打开 HTML 查看器查看进度、表格与验收内容；确认、评审、验收操作通过对话框发送文案，不改动工作单文件本身。

协作顺序：先读项目 AGENTS.md 和 DESIGN.md，再按工作流创建 workorders/T-YYYYMMDD-xxx.md；
可随时通过工作单助手，查看工作单进度、状态和验收证据。

06 / SINGLE SOURCE OF TRUTH

工作单：唯一真相，不是文档负担

每个需求一张工作单，存放在项目根目录 workorders/，命名为 T-YYYYMMDD-xxx.md。它贯穿需求、契约、切片、测试、验收和交付。

worksheet-template.md · 对话起手式
我有一个需求：<需求描述>。
请先按团队 AI 辅助开发工作流处理：
1. 判断场景 A / B，并给出低 / 中 / 高复杂度及理由；
2. 只做需求澄清，确认实现效果、边界、约束和可验证验收标准；
3. 将确认内容回填工作单，完整回显给我确认；
4. 未经我明确确认，不进入接口设计或实现。

注意：如果是一批不相关需求，请先按可独立交付的用户价值拆分，逐个建立工作单。

07 / GUARDRAILS

五条质量红线，任何速度都不能越过

01 · 不跳过测试与验收

没有先写测试、跑起来验证并按验收标准逐条对账，就不能宣称完成。

02 · 不未经确认修改公共契约

接口、字段、错误码和兼容边界必须先查、先定、先确认；破坏性变更不能直接改。

03 · 高复杂度不跳过契约设计

架构、契约、跨模块或多子系统需求，必须先完成书面化契约和验收门。

04 · 中高复杂度不跳过人工评审

工作单未完成评审，不得进入实现；评审未通过，回退修改工作单。

05 · 工作区不干净不开始新需求

新需求入口发现未提交改动时，AI 必须拒绝开始，不提供绕过选项；先提交或 stash，再重新检查。

落地前自检

AI 辅助开发的目标，不是替代工程判断，而是让工程判断更早、更清楚、更可复用。
