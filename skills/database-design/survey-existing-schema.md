# 存量盘点（Surveying Existing Schema）

场景 2（存量调整/新增）第一步必读；场景 1（新建）也用它做一次快速确认：**目标实体确实没有现成表/可复用结构**。

## 根本原则

**只读盘点，摸清现状才谈设计。** 猜存量结构 = 违规（SKILL.md 红线 1）。

盘点依据**只来自项目内文件/文档或用户提供的结构**；绝不连生产库、绝不凭代码"感觉"推断、绝不把"大概长这样"当现状写进设计稿。

## 何时使用

- 场景 2：任何存量变更之前，先还原当前真实结构
- 场景 1：开工前快速确认"没有现成可复用"
- 收到"帮我改表/加字段/加索引"但项目里从没见过相关表时

**何时不用**：项目结构完全已知且已确认（最近刚盘点过、无并发变更）——可跳过并注明依据。

## 盘点清单（按序）

1. **约定**：项目 AGENTS.md / 团队约定——引擎、字符集、迁移工具与命令、命名约定（表/字段/索引前缀）、是否启用外键、软删与审计字段（created_at/updated_at/deleted_at）、模型/DAO 组织方式。
2. **迁移文件目录**（如 `migrations/`）：按时间/版本顺序还原最新 schema；**记录已发布的最新迁移版本号**（后续新迁移要排在它之后）。
3. **结构文档**：schema.sql、初始化脚本、ER/表结构文档、接口文档里的字段定义。
4. **代码侧现状**（交叉印证，不作为唯一依据）：Go struct（model/entity）、DAO 标签（如 gorm 标签）等反映的字段。
5. **冲突初判**：本次要新增/修改的实体是否已有表？命名是否冲突？已有字段类型/语义是否与需求打架？

**盘不到**（无迁移文件、无文档、代码查不到）→ **停下，向用户要结构**，不猜、不硬画。

## 产出（写入设计稿「现状摘要」节）

- 表清单 + 关键表字段摘要（注明盘点到的范围与来源文件）
- 最新迁移版本 / 结构文件基线
- 发现的项目约定（命名/引擎/外键/软删/审计字段）
- 与目标实体的差异初判：已有冲突 / 无冲突 / 需用户澄清

## 常见错误 / 红旗

- 没有文件也硬画 schema，把假设当现状
- 只看了部分迁移就下结论（漏掉后续版本的变更，schema 已不同）
- 拿生产/他人环境的表当默认假设
- 盘点结论不落盘，下一轮对话里"凭记忆"继续设计

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "从代码里能猜个大概，不用问了" | 代码可能落后于库结构；猜 = 违规，盘不到就问 |
| "结构很简单，跳过盘点直接改" | 跳过盘点 = 不知道自己在改什么；成本最低的步骤最不能省 |
| "上次看过一次，还记得" | 文件是唯一真相，聊天记忆不算数；重新盘点或注明依据 |
