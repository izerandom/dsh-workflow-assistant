# 数据库与表设计（Database Design）

## 概述

独立的数据库设计技能，承担**助手 + 约束**双重角色：

- **助手**：通过澄清清单与多轮对话，把需求转成可评审、可落地的表设计与建库建表/迁移文件。
- **约束**：防止 AI 拍脑袋建表、猜存量结构、未经确认动破坏性变更。

面向 **MySQL**（模板默认 InnoDB / utf8mb4 / BIGINT 自增等）；引擎、迁移工具、命名约定、是否启用外键等**团队选择归项目 AGENTS.md**，本技能不越权代定。

**只产出设计文件 + DDL/迁移文件，不直接对任何库执行**；执行只能由人在显式授权的环境（如本地 dev 库）进行。

## 根本原则

1. **先盘点，后设计，再改动。** 设计新表前先确认没有现成可复用；动存量结构前先只读摸清现状。猜存量结构 = 违规。
2. **文件是唯一真相。** 设计决策写入设计稿/工作单，聊天记录不算数。
3. **确认闭环。** 每个新表、新字段、每个变更点都要**回显给用户确认**；"用户没反对 ≠ 已确认"、"用户提建议 ≠ 已放行"。
4. **不发明。** 不发明项目没有的迁移工具链、不硬造字段/表；可推断处给默认值并标注"假设"，用户可否决。
5. **生成 ≠ 完成。** 只产出文件时，验收 = 文件级逐条对账 + 人工评审；"未对真实库执行验证"必须写入遗留风险。

## 何时使用

- 新库/新表设计（建库建表需求）
- 存量结构调整/新增：加表、加列、改类型、改/加约束、加索引、写迁移文件
- 开发工作流内涉及持久化数据模型的任务（与 development-workflow 配合，见下）
- "这个表怎么设计 / 帮我加个字段 / 这个查询该建什么索引"类请求

**何时不用**：不涉及表结构的纯问答；要求直接操作生产数据库的请求（**硬边界**——永远拒绝并引导由人执行）。

## 入口：场景分流（先分类再动手）

判据：**目标实体在当前项目中是否已有表/结构？**

| 场景 | 判据 | 走什么 |
|---|---|---|
| 1 新建 | 目标实体在项目里没有对应表（或全新库） | 快速盘点确认无 → 读 `table-design-checklist.md` → 设计 → 产出建表文件 |
| 2 存量调整/新增 | 已有表结构，需加表/加列/改约束等 | 读 `survey-existing-schema.md` 盘点 → 读 `schema-change-checklist.md` → 差异设计 → 产出迁移文件 |
| 不确定 | 盘点后仍无法判断 | 以盘点结果为准；盘不到结构就停下问用户，**不猜** |

## 与 development-workflow 的关系

- 本技能**独立可触发**（单独对话直接可用），也可被 development-workflow 按需加载（其流水线涉及数据模型时）。
- 处于开发工作流内（已有工作单 `workorders/T-*.md`）时：设计决策**并入当前工作单**（补「数据库设计」节 + 变更记录留痕），完整设计稿另存 `designs/`，两者互相引用。
- 权威边界：本技能管**表设计域**；团队规范（引擎/字符集/命名/迁移工具）归项目 **AGENTS.md**；整体流水线纪律（人工评审门/验收）归 development-workflow。冲突时以更具体的约定为准，并把分歧记入变更记录。

## 多轮对话规则

- **不设轮次上限**，由用户主导终结；AI 不设硬性截止，但应主动提示"已可出稿评审"。
- 每轮只问"**用户必须拍板且影响面大**"的问题；可推断的（类型映射、通用审计字段、常规索引）由 AI 给默认值并标注"假设"，用户看到后可否决修改。
- **确认闭环**：本轮产出（字段表/变更点清单）完整回显 → 用户明确确认 → 才进入下一步/下一轮。
- **留痕**：每次调整先记入设计稿「变更记录」（时间/改了什么/为什么/决策人），再改内容。

## 产出物

| 产物 | 位置 | 说明 |
|---|---|---|
| 设计稿 | 项目根 `designs/T-YYYYMMDD-xxx-db.md` | 完整设计：现状摘要/实体与关系/字段表/约束索引/迁移计划/变更记录/验收对账。格式以 `schema-template.md` 为唯一权威 |
| 建表/迁移文件 | 按项目 AGENTS.md 迁移约定 | **已发布迁移不可改**，新变更 = 新迁移文件（up + down）；无约定时产出独立 `.sql` 草案（up/down 成对），不发明工具链 |
| 主工作单（开发请求内） | `workorders/T-*.md` | 补「数据库设计」节：引用设计稿 + 关键决策摘要；变更记录同步留痕 |

## 红线（任何场景都硬拒绝）

1. 未盘点就设计/改动；盘不到存量结构时**猜测**。
2. 自造字段/表/实体，未经用户确认。
3. 破坏性变更（删列/删表、改类型、收紧约束、加唯一约束）未经确认——先提示数据与调用方影响、给替代方案，再请求确认；不因用户催促豁免。
4. 直接修改已发布的迁移文件（新变更 = 新迁移文件）。
5. 试图连接生产库 / 索要生产凭据 / 以任何方式对库执行（Agent 无生产钥匙，执行只能由人）。
6. 跳过文件级验收对账就宣称"完成/已建好"。

## 验收（无执行前提下的定义）

1. 设计稿字段表与产出 DDL/迁移文件**逐条对账**：字段/类型/NULL/默认/约束/索引一一对应；无凭空字段、无命名与类型违规、无重复索引。
2. 每个迁移有对应 down/回滚；变更点与设计稿「变更记录」一致。
3. 中/高复杂度：交人评审（可借用 development-workflow 的独立评审规则）。
4. 设计稿「遗留风险」记录"未对真实库执行验证"，由后续实现切片的集成测试接住（不把执行验证这条线断掉）。

## 常见错误 / 红旗

- 一口气发明整库，无任何确认环节
- 存量变更不盘点直接写 ALTER，把"大概长这样"当现状
- 为图快直接改已发布迁移文件
- 数据丢失型变更（删列/删表/改类型）不提示影响
- 加 NOT NULL / 唯一约束前没有 backfill / 存量查重
- 把"文件生成好了"说成"表建好了"

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "表结构简单，不用逐条确认" | 字段是契约，错了改造成本极高；确认成本远低于返工 |
| "存量表我看代码猜一下就行" | 猜测 = 违规；盘不到就问用户要结构 |
| "用户说直接删列，我照做" | 破坏性变更先提示影响并请求确认，不因用户催促豁免 |
| "没有迁移工具，直接改 .sql 更快" | 已发布结构文件视同已发布迁移，不可改；新变更 = 新文件 |
| "字段名我想得比用户清楚" | 字段必须回显确认，禁止 AI 单方面发明 |
