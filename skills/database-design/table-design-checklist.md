# 新建表设计清单（Table Design Checklist）

场景 1（目标实体无对应表 / 全新库）使用。先用 `survey-existing-schema.md` 快速确认无现成可复用，再进本清单。

多轮规则见 SKILL.md：**每项标注 [必须问] 的才停下来问用户；标注 [默认+假设] 的由 AI 给默认值并标注"假设"，用户可否决**。所有产出逐行回显确认。

## 澄清清单（按序逐项）

### 1. 实体与关系 [必须问]

- 实体清单：每个实体一句话业务含义
- 关系与基数：1:1 / 1:N / N:M（落中间表）、级联与删除策略
- 边界：本次明确不做哪些（防范围蔓延）

### 2. 业务字段 [核心必须问，通用字段 AI 补]

- 每个实体的关键业务字段：业务含义、取值空间、是否业务唯一
- AI 补充通用/审计字段并标"假设"：`id`、`created_at`、`updated_at`（`deleted_at` 见第 8 项约定）
- 字段必须能与接口设计的数据契约、查询路径对齐；对不上的要追问，禁止凭空补字段

### 3. 主键策略 [必须问]

- 自增 BIGINT UNSIGNED / UUID / 雪花等——涉及跨系统引用、分表、数据同步时影响大
- 默认假设（无特殊需求）：单机 MySQL = `BIGINT UNSIGNED AUTO_INCREMENT`

### 4. 状态与枚举的表达 [必须问]

- 用 ENUM / 字典表 / 应用层常量 + VARCHAR？项目惯例优先（查 AGENTS.md），无惯例问用户
- 默认假设：`VARCHAR(20)` + 应用层常量（演进最省事），标注"假设"

### 5. 约束 [外键必须问；唯一约束必须问]

- **是否启用外键约束**：很多团队禁用、靠应用层保证一致性——查 AGENTS.md，无约定必须问
- **业务唯一键**（如 `user_id + sku_id` 唯一）：必须问，直接决定写入与报错路径
- NULL 策略：由业务语义定；AI 默认"业务必有值 → NOT NULL，可选值 → 可空"并标注"假设"

### 6. 类型与字符集 [默认+假设；特殊场景才问]

- 类型映射见 `schema-template.md` 类型速查；有歧义（金额/时间/大文本）时给出依据再定
- 字符集/排序规则：默认 `utf8mb4` / `utf8mb4_0900_ai_ci`（按 AGENTS.md，无则假设）
- 引擎：默认 InnoDB
- **金额必须 DECIMAL，禁止 FLOAT/DOUBLE**——违反即红旗

### 7. 索引 [AI 默认+假设；按查询路径推导]

- 每个索引必须能说出它服务**哪个查询/接口/唯一性约束**；说不出依据 = 不建
- 组合索引列顺序按查询条件的选择性与频率排
- 默认假设：外键列与高频查询过滤列加单列索引；覆盖索引按需补
- 产出里每条索引标注服务对象，供评审纠偏

### 8. 时间与审计字段约定 [查 AGENTS.md；无则默认+假设]

- 默认：`created_at` / `updated_at` 用 `DATETIME(3)`；由应用维护还是 DB 默认值/触发器，按项目惯例
- 软删 `deleted_at`：项目是否用软删？查约定，查不到**必须问**（影响所有查询语句）

## 产出（逐行回显）

按 `schema-template.md` 的字段描述表模板整理：

- 每个实体一张字段表（字段/类型/NULL/默认/约束/索引/含义与来源）
- 每行标注「已确认」或「假设」；「假设」行用户可一次性批量否决或修改
- 约束与索引单独成表，注明服务对象与决策依据
- 全部确认后进入迁移/建表文件设计与验收（见 SKILL.md）

## 常见错误 / 红旗

- 一口气发明整库，无任何确认环节
- 字段与接口数据契约对不上还硬建
- 索引凭空出现，说不出服务哪个查询
- 状态字段用 `TINYINT` 存语义却不留映射说明
- 金额用 FLOAT/DOUBLE

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "字段我先全建上，反正能加" | 表结构是契约，上线后加字段/改类型成本高；一次设计对，比上线后返工便宜 |
| "索引多建点没坏处" | 每个索引都有写入代价；说不出服务哪个查询 = 不建 |
| "用户只说了大概，我先按经验建" | 关键字段/关系必须问清；可推断的才给默认+假设 |
