# 存量变更清单（Schema Change Checklist）

场景 2（对已有表加表/加列/改类型/改约束/删列/加索引，产出迁移文件）使用。**必先读 `survey-existing-schema.md` 完成盘点**，再进本清单。

## 根本原则

**变更 = 差异 + 影响评估，不是直接写 ALTER。** 每个变更点先归类（见下表），破坏性变更先给影响与替代方案、请求确认，再设计迁移文件。已发布迁移不可改（SKILL.md 红线 4）。

## 变更分类与默认策略

| 变更 | 破坏性？ | 策略要点 |
|---|---|---|
| 新增表 | 通常非破坏 | 查重实体/命名冲突、对齐项目约定；一个内聚变更一个迁移 |
| 加列（可空 / 带默认值） | 非破坏 | 可直接出稿；大表加列注意锁表与维护窗口（按项目惯例提示） |
| 加列后收紧 NOT NULL | 发布期破坏 | **三步**：①加可空列 → ②应用/脚本回填存量 → ③收紧 NOT NULL；中间版本要兼容新旧应用同时跑 |
| 加唯一约束 | 可能破坏 | **先查存量重复数据**；有重复先给出清理方案，再请求确认 |
| 改类型 / 改长度 | 破坏性 | 数据转换与锁表影响；确认后单独迁移；down 写清转换规则 |
| 删列 / 删表 | 破坏性（数据丢失） | 必须确认无消费者（代码/接口/外部系统）；推荐**先停用后删**（两步） |
| 加索引 / 调整索引 | 非破坏 | 确认索引有查询路径依据、无重复索引；大表注意维护窗口 |

## 评估步骤

1. **盘点**：读 `survey-existing-schema.md`，记录最新迁移版本与约定。
2. **列变更点**：本次所有变更逐条列出——改什么 / 为什么 / 影响哪些已有数据与调用方（代码、接口、外部系统、已发布应用版本）。
3. **归类**：按上表逐条判定破坏性。
   - 非破坏 → 出稿回显确认。
   - 破坏性 → 先给影响说明 + 替代方案（两步发布 / 影子列 / 停用期），**请求确认后才设计迁移**；不因用户催促豁免（SKILL.md 红线 3）。
4. **设计迁移**：
   - up + down 成对；**已发布迁移不可改**，新变更 = 新迁移文件，编号排最新基线之后；
   - 命名与目录结构跟 AGENTS.md 约定；
   - **一个迁移只装一个内聚变更点**（评审与回滚都清晰）；
   - down 必须能把 up 完整还原（含数据回填的说明）。

## 兼容发布要点

- 迁移要兼容**新旧版本应用同时跑**的发布窗口：
  1. 先加可空列 / 新表（旧版本应用不受影响）；
  2. 应用灰度切换读写新列；
  3. 回填 / 校验存量；
  4. 收紧约束或删除旧结构。
- 涉及删除的列/表：先确认停用期已过、无消费者，再删。

## 常见错误 / 红旗

- 直接改已发布的迁移文件"补一笔"
- 加 NOT NULL 列没有 backfill 或默认值策略
- 加唯一约束前不查存量重复数据
- 删列/删表前没确认消费者
- 一个迁移里塞多个无关变更，导致无法独立回滚
- 破坏性变更没提示影响就开始写 ALTER

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "直接在旧迁移里加一行最快" | 已发布迁移被环境执行过，改了 = 环境与文件不一致；新变更 = 新文件 |
| "这列反正没数据，直接 NOT NULL" | 存量没数据也要证明；先查、再 backfill，流程不因"反正"跳过 |
| "删列的事用户点头了" | 破坏性变更确认要落在变更记录（谁/何时/确认了什么），口头点头不留痕 = 未确认 |
