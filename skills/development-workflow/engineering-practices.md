# 工程实践（Engineering Practices）

## 概述

语言无关的通用工程约束，适用于所有语言：模块/函数拆分、业务逻辑分离、复用、类型契约、命名原则。**具体语言约定（命名风格、工具链、框架）归项目 AGENTS.md。**

## 根本原则

代码是为"可测试、可复用、可维护"服务的，不是凑行数。**违反约束的字面就是违反其精神。**

## 何时使用

- 实现任何语言的任务时（后端 / 前端 / 脚本）
- 中/高复杂度切片（低复杂度也遵守，只是改动小）

## 约束

### 1. 模块 / 函数拆分

- 按"职责 + 可复用性 + 可测试性"拆，**不按行数/文件数**。
- 超过一个职责（如：取数 + 变换 + 输出）必须拆。
- 判据：能否独立测试？别处会不会复用？逻辑是否独立？
- 一个文件/函数堆所有 = 违规。

### 2. 业务逻辑与 IO / 框架分离

- 业务逻辑抽成纯函数 / 独立层，不让 IO、框架调用、格式化和业务逻辑混在一起。
- 判据："这段能不能独立写测试"——能就该抽出去。

### 3. 复用与重复

- 相同逻辑第二次出现必须抽（函数 / 模块 / 公共层）。
- 测试数据 / 样例不硬编码在业务代码里，独立文件并标注。
- 复制粘贴式复用 = 违规。

### 4. 类型与契约

- 用语言类型系统表达契约，禁止绕过类型：
  - TypeScript / Go：禁止 any / interface{} 滥用
  - C++：不用 void* 绕过类型系统
  - Lua（无静态类型）：用类型注解约定 + 运行时校验兜底
- 数据模型与接口契约对齐，不"猜"字段。
- mock / 测试数据字段与契约一致。

### 5. 命名

- 一致性优先，可读性高于简短；同一概念全项目同名。
- 具体命名约定（Go 导出驼峰、C++ 下划线、Lua snake_case 等）归项目 AGENTS.md。

## 常见错误 / 红旗

- 一个函数/文件几百行、多职责混在一起
- IO、框架调用混在业务逻辑里
- 复制粘贴式复用、测试数据硬编码在业务代码里
- 绕过类型系统、字段和契约对不上

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "这是最小示例，一个文件就够了" | 结构约束不因示例大小豁免；拆分判据是职责数，不是文件大小 |
| "图快，先堆一起后面再重构" | "后面再重构"几乎不会发生；一次到位，可测试性才成立 |
| "逻辑写在调用层里更直观" | 混在一起 = 无法独立测试、无法复用；判据是"这段能不能独立写测试" |
| "mock/样例混在业务里更方便" | 必须独立文件并标注；混在业务里接真数据时必踩坑 |
