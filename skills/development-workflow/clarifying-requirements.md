# 需求澄清（Clarifying Requirements）

## 概述

把一个模糊或初步的需求，变成"效果、边界、验收标准"都明确的确认需求。产出物是**验收标准**——必须可观测、可验证，供流水线末端的"验收"对账。确认结果**回填工作单**，后续步骤只读工作单。

## 根本原则

**验收标准没定清楚之前，不进入接口设计或实现。** 没有"边做边想清楚"的例外。

**修改必须回显确认**：用户提出修改 → 更新工作单「需求」节 → **把修改后的内容完整回显给用户** → 用户明确确认后才进入下一步。用户提建议 ≠ 已确认。

## 何时使用

- 一个内聚需求已分类（场景 A / 场景 B 拆分后），准备进流水线
- 需求只说清了"要什么"，没说清"做完是什么样、不做什么"

**何时不用**：低复杂度单点小改——一句话确认即可，不做完整对话。

## 澄清清单（按需逐条确认）

1. **实现效果**：做完之后，用户能看到/用到什么？
2. **边界**：哪些算本次范围，哪些明确不做？
3. **约束**：性能、兼容、依赖、时间等硬约束？
4. **验收标准**：怎么算"做完了"？每条都要可观测、可验证（能写进测试）。

## 验收标准产出要求

- 每条 = 一个可观察行为，能被测试或人工核对。
- 禁止模糊词："尽量""大概""基本可用"。
- 没有验收标准的需求 = 未澄清，退回继续问。

## 按复杂度伸缩

| 级 | 需求对话做法 |
|---|---|
| 低 | 一句话确认效果 + 一条验收标准 |
| 中 | 完整澄清清单 + 明确验收标准 |
| 高 | 完整清单 + 验收标准书面化，边界/非目标显式记录 |

## 常见错误 / 红旗

- 跳过验收标准直接进入实现
- 验收标准用模糊词（"可用""完善"）
- 把"要做什么"当成了"做完是什么样"
- 边界没定就动手，范围一路膨胀
