# 接口设计（Designing Interfaces）

## 概述

在动手实现前，先查已有契约、再定新契约：接口签名、数据契约、兼容边界。产出物是**契约**——实现必须遵守、改动需确认。

## 根本原则

**先查已有契约，再设计新契约。** 设计新接口前必须检查项目是否已有接口文档、后端定义、团队约定——已有则直接复用对齐，禁止另造一份；确无才设计新接口，且字段/结构需与用户确认，禁止自己发明字段。**契约未定之前不进入任务拆分。** 公共契约未经确认不得改动。

## 何时使用

- 需求已澄清（有验收标准），准备进入任务拆分
- 涉及新接口、数据结构、协议，或跨模块交互

**何时不用**：低复杂度单点小改（无接口/契约变化）——跳过此步骤。

## 设计前先查（复用优先）

1. 查项目接口文档：OpenAPI / Swagger、接口文档目录、AGENTS.md 约定。
2. 查后端是否已有对应接口 / 字段定义。
3. **已有 → 直接复用对齐，不新造；确无 → 才设计新接口。**
4. 新接口的字段 / 结构必须与用户确认，禁止自己发明字段。

## 要定清什么

1. **接口签名**：函数/端点/消息的输入输出。
2. **数据契约**：字段、类型、格式、约束。
3. **协议约定**：调用时序、错误处理、幂等/重试。
4. **兼容边界**：哪些是稳定契约不能破，哪些是内部实现可改。

## 契约测试

- 契约必须可被契约测试逐条断言（每个 API / 字段 / 错误码都有对应断言）。
- 破坏性变更未同步更新契约测试 = 不允许合入。

## 按复杂度伸缩

| 级 | 接口设计做法 |
|---|---|
| 低 | 跳过（无契约变化） |
| 中 | 定接口签名 + 数据契约 |
| 高 | 契约书面化 + 兼容边界显式记录 + 验收门 |

## 常见错误 / 红旗

- 跳过硬边界直接实现（尤其是高复杂度）
- 不查已有接口文档，自己发明接口 / 字段
- 改了公共契约不确认
- 把内部实现细节写进契约，限制后续重构
- 兼容边界不清，改了稳定契约导致调用方崩

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "用户要求直接改，我照做就行" | 公共契约改动 = 破坏性变更；先定契约、提示影响并确认，不因用户要求豁免 |
| "仓库内调用方都改了就行" | 公共契约的消费方可能在仓库外；只改仓库内 ≠ 安全 |
