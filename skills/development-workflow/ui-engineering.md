# UI 约束（UI Engineering）

## 概述

前端 UI 专属约束。**语言无关的通用工程原则（模块/函数拆分、业务逻辑分离、复用、类型契约、命名）见 `engineering-practices.md`**，本文件只列前端特有部分。团队特定选择（组件库、目录结构、命名特例）归项目 AGENTS.md，设计令牌归项目 DESIGN.md。

## 根本原则

UI 代码是为"可测试、可复用、可维护、可访问"服务的，不是凑行数或凑视觉。**违反约束的字面就是违反其精神。**

## 何时使用

- 实现任何前端 UI 组件 / 页面时
- 非 UI 任务（后端 / 脚本）只读 `engineering-practices.md`，不读本文件

## 约束

### 1. 组件粒度（前端应用）

- 通用拆分原则见 `engineering-practices.md` §1。
- 前端特有：超过一个职责（渲染 + 拉数据 + 状态变换）必须拆组件。
- 判据：能否独立测试？别处会不会复用？

### 2. 逻辑 / 视图分离

- 模板/JSX 里禁止业务逻辑：fetch、状态变换、格式化、复杂分支。
- 逻辑抽 hooks / 组合式函数 / 纯函数 / 容器组件；展示组件只负责渲染。

### 3. 前端命名

- 组件名名词、文件与组件同名。
- handle 前缀事件处理 / on 前缀回调 props / is·has 前缀布尔。

### 4. 状态覆盖

- 数据驱动组件必须有**加载态、空态、错误态**（不只是正常态）。
- 边界数据兜底：超长文本截断、特殊字符转义、0 值、null/undefined。
- 判据：**删掉数据看页面崩不崩**——崩就是没覆盖。

### 5. 交互体验

- 响应式：至少覆盖桌面 + 移动两个断点，不是"勉强能看"。
- 可访问性：语义化标签、键盘可操作、焦点可见、对比度达标（aria 补足交互组件）。
- 表单：校验提示 + 提交反馈（成功/失败/禁用态）。

### 6. 视觉一致性（行为层）

- **动手前先读项目 `DESIGN.md`**——它定义了设计令牌的唯一真相和消费方式（工具类 / CSS 变量 / JS 常量 / 组件库变量），照它引用，禁止发明值。
- 颜色/间距/字号/圆角用**设计令牌**，禁止硬编码（令牌值和消费方式在项目 DESIGN.md）。
- 优先复用现有组件/样式类，不重复发明。

## 常见错误 / 红旗

- 一个文件几百行、多职责混在一起
- fetch / 状态变换写在模板/JSX 里
- 只有正常态，空态/错误态/加载态缺失
- 硬编码颜色/间距，不用设计令牌
- 移动端"勉强能看"、无键盘操作、表单无校验反馈
