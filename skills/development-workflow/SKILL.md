# 开发工作流（Development Workflow）

## 概述

每个开发请求都先分类、再走流水线、按执法规则执行。本 skill 是团队 AI 工作流的**唯一可执行权威**，流水线各步骤的完整规则在同文件夹的步骤文件里，按需读取。

## 根本原则

**违反规则的字面就是违反规则的精神。** 没有"按精神执行"的例外。

**确认闭环**：用户提出的任何修改，AI 改完工作单后必须**回显给用户确认**，用户明确确认后才进入下一步。**"改了" ≠ "确认了"**——用户提修改建议不等于已确认，不能把修改动作当成放行信号。

## 工作单（唯一真相）

每个需求一张**工作单**，贯穿整个流水线：需求、验收标准、边界、切片、测试用例都记进去。AI 每轮只读工作单 + 相关代码，**不靠聊天记忆**——聊天记录不算数，文件才算数。用 `worksheet-template.md` 模板，新需求先复制一份，存到项目根目录 `workorders/`，命名 `T-YYYYMMDD-xxx.md`。

**位置与格式（唯一权威）**：

- 新工作单**一律**放项目根目录 `workorders/`，命名 `T-YYYYMMDD-xxx.md`。**不沿用项目里任何旧路径**——旧工作单放错位置不代表新单也放那。
- 格式**以 skills 里的 `worksheet-template.md` 为唯一权威**；**禁止参考项目里已有工作单的格式**——它们可能是旧版本。发现旧格式/旧路径工作单时：新单照模板来，旧单可提示用户处理，但不模仿、不照抄。

**工作单生命周期**：
- 需求**进行中**（未完成）的调整 → 走回退机制，更新**当前**工作单。
- 需求**已完成后**的新请求（哪怕很小，如改权限）→ 是**新需求**，**新建工作单（新 T-编号）**，旧单归档**只读不改**。
- 收到修改请求且已有工作单时：先判断是"未完成需求的调整"还是"已完成功能的新变更"；已完成的一律开新单。

## 何时使用

- 收到开发请求：功能、缺陷修复、重构、一批请求
- **变更/修改已实现功能的请求（哪怕很小）——同样走流水线，按复杂度分级：简单走简化路径，重走完整路径**
- 开始、恢复或继续实现之前
- 需要拒绝或重定向的请求

**何时不用**：纯问答、查状态、与代码改动无关的对话——直接回答，不进入流水线。

## 硬边界（永远拒绝，并引导）

- **不生成新项目脚手架**——引导到现成项目模板（如 create-vite / create-next-app / degit）选型；模板自带 AGENTS.md 负责技术栈 + 团队代码风格。
- **不维护模板目录、不推荐技术栈**。
- **不覆盖团队规范**——技术栈、代码风格归项目 AGENTS.md，本 skill 只负责"AI 怎么干活"。

拒绝 ≠ 推走，是**澄清 + 重定向**：说明"这不在本工作流职责内"，引导到正确工具，然后无缝接管后续。

## 治理底线（安全不可妥协）

- **权限边界**：Agent 只能写工作区/分支，永远没有生产环境钥匙；发布只能由人执行。
- **数据合规**：敏感数据脱敏后才能进入 prompt / 喂给外部模型；涉密项目按公司规范禁止外发。

## 请求分类（入口，先分类再进流水线）

### 第 1 步：场景 A / B

判据：**每个请求能否独立交付用户价值？**

- 能独立交付 → **场景 B**：先做**需求级拆分**，得到 N 个内聚需求，**一次只做一个**，逐个走流水线。
- 不能独立交付（必须一起才有价值）→ **场景 A**：一个内聚需求，直接进流水线。

### 第 2 步：复杂度三级

判据：**影响范围 + 是否触碰契约/边界**（不看文件数）。影响范围 = 改动的调用面/数据面。

| 级 | 判据 | 走什么 |
|---|---|---|
| 低 | 单点小改：文案、bug、单文件、无契约变化 | 简化路径：需求一句话确认 → 先写测试 → 实现 → 跑测试 → 验收 |
| 中 | 内聚功能：多文件、有数据/接口、可拆子任务 | 完整流水线 |
| 高 | 架构/契约/跨模块/多子系统 | 完整流水线 + 契约书面化 + 验收门 |

裁剪的是步骤/文档数量，不是质量底线。至少保留两条：**验收标准可测** + **跑起来验证过**。

## 流水线

```
需求对话 → 接口设计 → 任务拆分 → [中/高]人工评审工作单 → 每个子任务循环(先写测试 → 实现 → 跑测试通过 → [中/高]独立评审 → 验收)
```

- **需求对话**：**REQUIRED:** 读 `clarifying-requirements.md` 确认实现效果、边界、做什么/不做什么，产出**验收标准**（供末端验收对账）。
- **接口设计**：**REQUIRED:** 读 `designing-interfaces.md` 定接口签名、数据契约、兼容边界。
- **任务拆分**：**REQUIRED:** 读 `decomposing-tasks.md` 把内聚需求拆成可测试子任务（含每切片测试用例）。
- **人工评审门**（中/高复杂度，必过）：工作单完整后（需求/边界/契约/切片/测试用例）交人评审；未通过 → 回退修改工作单，**不进入实现**。低复杂度只做需求一句话确认。
- **循环**：每个子任务先写测试 → 实现 → 跑测试通过 →（中/高复杂度）独立评审 → 验收，逐个循环。
- **工程约束**（通用，所有语言）：**REQUIRED:** 读 `engineering-practices.md` 遵守模块/函数拆分、业务逻辑分离、复用、类型契约、命名原则。
- **实现约束**（涉及 UI 时）：**REQUIRED:** 另读 `ui-engineering.md` 遵守组件、模板/JSX 分离、状态覆盖、交互、视觉等前端专属约束。
- **独立评审**（中/高复杂度）：**REQUIRED:** 读 `reviewing-independently.md` 独立评审，评审者不读实现者上下文，只读代码与契约。

**回退**：实现/测试中发现设计错误 → 回退到"接口设计"重做；高复杂度回退需人确认。**每次回退/调整当前工作单内容前，先把变更记入工作单「变更记录」（时间/改了什么/为什么/决策人），再改内容**——聊天里的决策必须沉淀到文件。

## 执法与拒绝

- **质量红线（任何复杂度都硬拒绝）**：
  1. 跳过测试/验收就宣称完成
  2. 未经确认修改公共契约（即使用户说"直接改"，也要先提示破坏性影响、请求确认）
  3. 高复杂度跳过契约设计
  4. 中/高复杂度跳过工作单人工评审就进入实现
- **其余偏离随复杂度伸缩**：低 → 放行/轻提醒；中 → 缺关键步骤警告；高 → 缺契约/验收硬拒绝。

## 测试与验收

- **测试**：**REQUIRED:** 读 `writing-tests.md` 先写测试再实现（TDD）+ 测试技法（类型/测什么/AAA/覆盖）。
- **跑起来验证**：AI 说"通过"不算，本地跑起来亲眼确认（页面/接口/命令输出）才算。
- **验收**：**REQUIRED:** 读 `verifying-completion.md` 按验收标准自验，中/高复杂度交人最终确认。

## 快速参考

| 请求 | 分类 | 动作 |
|---|---|---|
| 生成新项目 | 硬边界 | 拒绝 + 重定向到现成模板 |
| 一批不相关需求 | 场景 B | 需求级拆分，逐个走流水线 |
| 实现某功能（如 CRUD） | 场景 A · 中 | 完整流水线 |
| 改一行文案 | 低 | 简化路径 |
| 改公共 API | 高（触契约） | 完整 + 契约书面化 + 验收门 |

## 常见错误 / 红旗

- 把"一批不相关需求"当成一个内聚需求一次做完
- 用文件数判断复杂度
- 跳过测试/验收就宣称完成
- 把团队规范（代码风格）写进本工作流，覆盖项目 AGENTS.md

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "替用户选好技术栈是为'尽快、最小'" | 不生成脚手架、不推荐技术栈；选型让用户拍板，AI 只给选项+理由+风险 |
| "知道该拆，但已经一口气做完了" | 场景 B 先需求级拆分、一次只做一个；不能做完才在反思里说该拆 |
| "用户明确要求直接改，我照做+报告风险就行" | 未经确认改公共契约是硬红线；先提示破坏性影响并请求确认，再动手 |
| "文件数少就是低复杂度" | 复杂度看影响范围+契约，不看文件数 |
