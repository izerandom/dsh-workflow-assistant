# 提示词优化（Prompt Optimization）

## 概述

把"一句话的模糊需求"变成"一份自包含、可直接粘贴执行的完整提示词"。本 skill 只负责**把需求问清楚、写清楚**，不负责实现、不做任务拆分、不选技术方案。

## 根本原则

- **上下文里能查到的不问用户，用户没说的一律标明来源。**
- **需求没问清楚之前，不输出成品提示词。** 没有"边写边定、差不多就行"的例外。
- **成品必须自包含**：脱离本次对话也能被读懂——粘到新会话里就能用。聊天记录不算数，提示词文本才算数。

## 何时使用

- 用户需求模糊、笼统、只有一句话
- 用户明确要求：帮我理一下需求 / 写个提示词 / 优化这个 prompt
- 需求里出现"优化一下""完善下""做个类似 XX 的"这类无法直接执行的表述

**何时不用**：需求已完整（可直接放行）、纯问答与查状态、与产出无关的闲聊。

**职责边界**：

- **不做**：写工作单、拆任务、定接口契约、选技术栈、直接实现——这些归 `development-workflow`
- **不覆盖团队规范**：技术栈与代码风格归项目 AGENTS.md，本 skill 只负责"把需求说清楚"

## 硬规则

1. **不编需求**：无法从用户输入或项目文件推导的细节，一律进「待确认」，**不写进成品提示词正文**。
2. **短路规则**：需求已具备清晰的目标、边界、可验证验收标准时，**直接放行**——给提示词或建议进入开发工作流，不做仪式化重写。
3. **待确认非空，不输出成品**：先解决阻塞项；用户明确接受某条假设为默认时，把它降级为正文的有效内容，而不是留着。

## 流程

```
0 判断适用性 → 1 探查与声明 → 2 理解回显 → 3 只问阻塞问题 → 4 起草骨架 → 5 逐条确认 → 6 交付
```

### 0. 判断适用性

- 需求**已完整**（目标、边界、验收都清楚）→ **直接放行**：给一份提示词，或建议进入 `development-workflow`，不重写。
- 纯问答、查状态、与产出无关 → 不启动本 skill。
- 模糊需求，或用户明确要求梳理 → 继续。

### 1. 低成本探查与声明

**先声明，再读取**：说出打算参考哪些文件（如 `AGENTS.md`、`package.json`、目录结构、同类模块），用户可否决或补充范围。

再按需读取，只读与需求相关的部分：

| 优先级 | 读什么 | 拿来干什么 |
|---|---|---|
| 1 | 项目 `AGENTS.md` / `README.md` | 取技术栈、目录规范、团队约定 |
| 2 | 构建与依赖配置（`package.json` 等） | 取已有依赖与脚本，避免重复造轮子 |
| 3 | 目录结构 | 判断代码该落在哪、是否已有同类实现 |
| 4 | 同类模块的现有实现 | 沿用既有模式，而不是另起一套 |
| 5 | 用户明确提到的文件 | 需求直接相关的上下文 |

**非代码项目或非开发场景**：自动降级为纯需求澄清，不强行扫描项目。

### 2. 理解回显（先确认"我读懂的是不是你想要的"）

直接回显，不提问：

- 一句话：我理解你要的是「……」
- 我读到的上下文：文件 → 关键信息（一两行，不复述全文）
- 我已识别的缺口：还差哪几点没定

### 3. 只问阻塞性问题

判据：**不回答就会导致产出方向性错误**。事实类问题一律不问——自己去读。

按优先级排序，最多 5 个，能合就合：

1. 范围边界：做什么 / 明确不做什么
2. 完成判据：什么算做完了；有没有可观测的验收标准
3. 约束：技术、兼容、性能、依赖、风格上的硬约束
4. 现状与目标差距（改已有 / 新建）
5. 交付形式：产物形态与位置

### 4. 起草骨架

按下方骨架起草完整提示词，每条内容对应到来源。

### 5. 逐条回显确认

- 逐条回显给用户确认，**用户改哪条改哪条**
- 改完再回显一次，用户明确确认后才进入交付
- 用户提修改建议 ≠ 已确认

### 6. 交付

- 代码块：**可直接复制**的完整提示词
- 来源说明表：每个条目来自 `用户` / `项目`（注明文件）/ `假设`
- 「待确认」清单：仍未解决的点；若非空，**说明为何不能输出成品**并追问
- 交接：产出类需求 → 成品已含「执行方式」，接收方按其执行；用户可复制投喂，或落盘后由接收方读文件执行

## 提示词骨架（成品结构，也是澄清清单）

| 字段 | 要求 |
|---|---|
| 目标 | 做完之后用户能看到 / 用到什么 |
| 项目上下文 | 项目现状 + 相关文件、接口、既有约定 |
| 需求细节 | 拆到可执行粒度，具体到能动手 |
| 明确不做 | 防范围蔓延，显式列出 |
| 约束 | 技术 / 兼容 / 性能 / 依赖 / 风格 |
| 验收标准 | 每条可观测、可验证，供末端对账 |
| 交付形式 | 产物形态与位置 |
| 执行方式 | **仅开发类与产出类需求**：接收方必须走的流程（见下节） |

**复杂需求可按需要追加**：场景与角色、输入输出示例、参考资料、优先级排序。

## 「执行方式」是成品的一部分（不是交接时口头补的）

**接收方 AI 只看得到提示词，看不到本次澄清对话。** 成品里只写"就地修改"，它就会直奔实现——实测发生过：提示词没声明执行方式，接收方 AI 跳过工作单直接改代码。用户在对话里叮嘱"要走工作流"没有用，那句话不在提示词里。

**判据**：需求会**产出代码或其他交付物** → 必写「执行方式」；纯分析、纯问答、纯建议 → 不写。

**写法**：

- 开发类需求：`执行方式：先加载 development-workflow 技能并按其流程执行（建工作单 → 工作单评审通过 → 再实现），不得跳过工作单直接改代码。`
- 非开发类但需产出交付物：写明期望的作业流程。
- 纯分析 / 建议类：不写此字段，只写「交付形式」。

**项目有自己的工作流约定时**（如项目内 `.agents/skills/`、AGENTS.md 规定的流程），「执行方式」必须以**项目的约定为准**，不得默认套用 development-workflow。

## 来源标注与「待确认」

- **成品块内不写标记**：提示词保持可直接粘贴。
- **块外用来源说明表**：标出哪些内容来自用户、哪些来自项目文件、哪些是 AI 补的假设。
- **假设必须带依据**：`假设：依据 XXX`，泛泛的"根据经验"不算依据。
- **无法推导的 → 待确认**：连同"为什么这点会改变结果"一起问，不凭感觉挑提问对象。

## 验收标准口径

验收标准的写法**与 `development-workflow` 的 `clarifying-requirements.md` 对齐**：可观测、可验证、能写进测试；禁止"尽量""大概""基本可用"这类模糊词。本 skill 产出的验收标准可直接被下游工作单沿用，不另起一套。

## 产出落地

- **默认**：只在对话输出，不落盘。
- **落盘**（用户要求，或需求复杂到需要留档复用）：写入项目根 `prompts/`，与 `workorders/` 分开，命名 `P-YYYYMMDD-xxx.md`。

## 按复杂度伸缩

| 级 | 做法 |
|---|---|
| 低（单点小改、文案） | 一句话确认 + 简版提示词，不做完整骨架 |
| 中（内聚功能） | 完整五步 + 完整骨架 |
| 高（架构 / 跨模块 / 契约） | 完整流程 + 显式「明确不做」+ 落盘留档 |

裁剪的是步骤与篇幅，不是质量底线。至少保留两条：**验收标准可测** + **成品自包含**。

## 常见错误 / 红旗

- 把 AI 自己的假设当成用户需求写进成品，让用户"签字"
- 项目文件里能查到的事实（技术栈、目录约定）还去问用户
- 需求没澄清完就输出成品提示词
- 用"优化一下""完善下""差不多"这类模糊词充当验收标准
- 把本 skill 当成实现入口：开始拆任务、定接口、写代码
- 需求已经完整，还硬走一遍澄清仪式
- 产出类需求的成品缺「执行方式」：接收方 AI 会直接开始改代码，跳过项目工作流
- 项目已有自己的工作流约定，却仍在「执行方式」里套用 development-workflow
- 给纯分析 / 建议类需求硬加「执行方式」

## 合理化借口表

| 借口 | 反驳 |
|---|---|
| "用户赶时间，先给一版成品，缺口回头再补" | 缺口未定的成品会把不确定性带进实现；先把阻塞项问清，其余标注即可 |
| "这条细节很明显，用户肯定是这个意思" | 未确认的推断一律标为假设并确认；"很明显"不是依据 |
| "项目文件里有，我凭印象写就行" | 上下文必须真读过；没读就写 = 编需求 |
| "反正是提示词，写得模糊点让下游 AI 自己发挥" | 提示词的模糊会原样传递成实现的偏差；模糊处正是要问清的地方 |
| "顺手把技术方案也定了，省得用户再想" | 方案选型不是本 skill 职责，交回用户或下游工作流 |
| "执行方式在对话里说一句就够了，写进提示词太啰嗦" | 接收方 AI 看不到本次对话，只看到提示词；口头叮嘱等于没叮嘱 |
| "提示词写得越具体，接收方执行得越准" | 具体的是需求，不是流程；把改动点写得像施工单，接收方就越过工作流直接改——需求要具体，「执行方式」必须显式 |
| "项目那套流程我大概知道，照默认写就行" | 执行方式以项目约定为准；没读项目约定就写 = 编流程 |
